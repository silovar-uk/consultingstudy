# 0. このプロダクトでつくるもの

## 仮称

**Consulting Fundamentals Atlas**  
日本語名: **コンサル一年目の実戦教科書**

## 一文でいうと

> 「コンサルとして考える・読む・伝える・進める」を、読むだけでなく、解いて、つくって、振り返って身につけるための教科書型Webアプリ。

## 完成形のイメージ

単なる読み物ではない。以下の5つが一つにつながる学習環境にする。

```text
教科書
  ↓ 理解する
問題集
  ↓ 解いて弱点を特定する
実務演習
  ↓ Excel・スライド・メモをつくる
学習ログ
  ↓ いつ、何を、どこで間違えたか残す
AI振り返り
  ↓ 間違い方・思考の癖・次の学び方を言語化する
```

## 目指す到達状態

一年目の終わりに、以下を自分で回せる状態。

- 曖昧な依頼を、意思決定すべき問いに変えられる
- 事業の儲け方と、財務数値の変化をつなげて説明できる
- 公開情報・定量データ・インタビューから根拠を集められる
- 事実、解釈、仮説、提言を混ぜずに整理できる
- Excelで集計・検算・比較・簡易モデルをつくれる
- PowerPointで、相手が判断しやすい資料をつくれる
- 会議・タスク・リスクを管理し、小さな担当領域を自走できる
- 自分の弱点を把握し、必要な演習へ戻れる

# 1. この設計で大事にする原則

## 1-1. 用語暗記ではなく「判断できる状態」をゴールにする

フレームワークを知っているだけでは弱い。

```text
知っている
  ↓
説明できる
  ↓
例題で使える
  ↓
実在企業・実務ケースで使える
  ↓
相手の意思決定を前に進められる
```

各章は、必ずこの段階を上がれるように設計する。

## 1-2. 財務分析は「会計の勉強」で終わらせない

財務分析の最終目的は、数字を正しく計算することではない。

```text
事業はどう儲かっているか
  ↓
何の数字が動いたか
  ↓
なぜ動いたか
  ↓
それは一時的か、構造的か
  ↓
何を確認・判断・提案すべきか
```

この因果をたどる力を、財務トラックの中心に置く。

## 1-3. 「読む→解く→つくる→振り返る」を最小単位にする

1レッスンは、以下の流れで完結させる。

```text
10分: 読む
5分: 例を見る
10分: 小問を解く
20〜45分: 実務演習をつくる
3分: 自己採点・振り返り
```

## 1-4. 学習は一本道ではなく、弱点に戻れる地図にする

財務が苦手な人は、P/Lまで進んでも、実は「利益率」「増減率」「分母」の理解で止まることがある。

そのため、目次は線形の章立てで見せつつ、内部は前提スキルを結んだ**スキルグラフ**として扱う。

```text
売上構造
  ├─ 単価 × 数量
  ├─ 構成比
  ├─ 増減率
  └─ セグメント

営業利益
  ├─ 売上総利益
  ├─ 固定費・変動費
  ├─ 販管費
  └─ 限界利益
```

## 1-5. 正誤だけでなく「間違い方」を記録する

間違いは、すべて同じではない。

- 用語を知らなかった
- 計算を間違えた
- 分母・期間を取り違えた
- 問われていることを読み違えた
- 数字は読めたが、事業との接続が弱い
- 事実と推測を混ぜた
- 打ち手を飛躍させた

この分類を残すことで、AI振り返りも「もっと復習しましょう」ではなく、具体的になる。

## 1-6. 実務で使える成果物を蓄積する

各章に、必ず一つ以上の成果物を置く。

- 依頼確認メモ
- 論点ツリー
- 財務診断シート
- 競合比較表
- インタビューガイド
- 会議アジェンダ
- 議事録
- 課題・リスク管理表
- 提案スライド
- 実行ロードマップ

学習履歴ではなく、**実務ポートフォリオ**が残る構造にする。

# 3. 教科書の章立て案

## 3-1. 構成の考え方

財務を最初から重く置く。ただし、財務だけを先に詰め込むと「数字の意味を問う力」が育ちにくい。

そのため、最初に問題解決の最低限だけを置き、その後に財務分析へ集中する。

```text
Part 0〜I: 学習の土台を作る
Part II: 財務分析を集中的に学ぶ
Part III〜VI: 財務を事業・分析・資料・PMと接続する
Part VII: 統合ケースで使える状態にする
```

- 到達点: 営業CF、投資CF、財務CFの意味を説明し、利益と現金のズレを指摘できる

# 4. 財務分析トラックの学習順

財務が苦手な人向けに、Part IIは単発の章ではなく、七つの関門として見せる。

```text
Gate 0｜計算と数字の言葉
  └─ 増減率、構成比、利益率、単価、数量、期間、分母

Gate 1｜事業の儲け方
  └─ 売上は何で決まり、どこで利益が生まれるか

Gate 2｜P/L・B/S・C/F
  └─ 三表を個別に読める

Gate 3｜三表の接続
  └─ 事業活動と資金の動きを一つの話として読める

Gate 4｜指標・比較・推移
  └─ 成長性、収益性、安全性、効率性を比較できる

Gate 5｜仮説と経営論点
  └─ 数字から「なぜ」「次に何を確認するか」を出せる

Gate 6｜総合演習
  └─ 1社を通して診断し、8枚で伝えられる
```

## Gateの通過条件

- Gate 0: 計算式を見ずに、分母・単位・期間を説明できる
- Gate 1: 任意の企業について「誰に何を売り、何が利益を左右するか」を書ける
- Gate 2: 三表の主要項目を、自分の言葉で説明できる
- Gate 3: 売上増・設備投資・在庫増・借入増の三表への影響を追える
- Gate 4: 3社比較で、見るべき指標を選べる
- Gate 5: 断定を避けつつ、確認仮説を三つ出せる
- Gate 6: 根拠を明記した財務診断ミニデックを完成できる

## 財務だけの特別ルール

- すべての設問で「分母」「期間」「単位」を確認する
- 指標は、原則として前年・競合・業界特性のいずれかと比較する
- 数字から理由を断定しない。必ず「仮説」「追加確認事項」を分ける
- 財務情報だけで企業を断じない。顧客、競争、組織、投資、制度も確認する
- 公開情報を使う演習では、出所と公表日を必ず残す

# 6. 問題設計

## 6-1. 問題の種類

### A. クイックチェック

- 目的: 用語・基本概念・計算の取り違えを早く見つける
- 所要: 1〜3分
- 例: 正誤、選択、並び替え、穴埋め

### B. 理由を説明する問題

- 目的: 暗記と理解を分ける
- 所要: 3〜10分
- 例: 「営業利益が増えたのに営業CFが悪化する理由を三つ挙げる」

### C. 数字を読む問題

- 目的: 表・グラフ・開示資料を見て、変化と論点を拾う
- 所要: 10〜20分
- 例: 「3年分のP/Lから、最初に確認すべき論点を優先順で示す」

### D. 成果物をつくる問題

- 目的: 実務で再利用できる型を身につける
- 所要: 20〜60分
- 例: 財務診断メモ、競合比較、会議アジェンダ、WBS

### E. スペシャル問題

- 目的: 苦手・目標・担当領域に応じて、難易度と条件を変える
- 所要: 10〜90分
- 例:
  - 数字が苦手: 分母・単位・増減率だけに集中する短問
  - 財務を仕事で使いたい: 決算短信を読み、経営論点を出す
  - 企画職寄り: 事業KPIからP/Lへつなげる
  - PMO寄り: プロジェクト収支と進捗悪化を読む
  - 戦略寄り: 競合比較と資本配分まで考える
  - 時間がない: 15分限定の「一枚メモ」演習

## 6-2. 設問に持たせる属性

```json
{

  "chapter_id": "finance-09",
  "type": "data_reading",
  "difficulty": 2,
  "estimated_minutes": 10,
  "skills": ["pl_reading", "gross_margin", "fact_vs_hypothesis"],
  "prerequisites": ["growth_rate", "margin"],
  "formats": ["table", "short_answer"],
  "special_tags": ["finance_focus", "short_session"],
```

## 6-3. 回答時に記録するもの

正誤だけを残さない。

```json
{
  "question_id": "finance-pl-001",
  "attempted_at": "2026-07-04T16:00:00+09:00",
  "answer": "...",
  "is_correct": false,
  "confidence": 2,

  "self_note": "利益率の前年差を売上高の前年差と混同した",

```

## 6-4. 間違いの分類

```text
knowledge_gap      用語・概念が曖昧
calculation_error  計算ミス
unit_error         単位・桁・通貨の取り違え
period_error       期間・前年比・累計／単期の取り違え
denominator_error  分母の取り違え
reading_error      問題文・表・注記の読み落とし
logic_error        因果・論理の飛躍
comparison_error   比較対象が不適切
fact_hypothesis_mixed  事実と仮説の混同
communication_error    読み手に伝わらない表現
execution_error        手順・ファイル・確認漏れ
```

# 8. AI振り返りの役割

## AIに任せること

- 間違いの傾向を集計する
- 自己メモを要約する
- 次週の復習メニューを作る
- 回答の論理の飛躍、根拠不足、事実と仮説の混同を指摘する
- 提出物をルーブリックに沿ってレビューする
- 「次に確認すべきこと」を質問として返す

## AIに任せないこと

- 出所不明の財務数値を事実として断定すること
- 公開情報を読まずに、企業評価をもっともらしく生成すること
- ユーザーの回答を唯一の正解／不正解として過度に断定すること
- 機密情報・個人情報・未公開情報を前提にした学習分析

## AI振り返りの出力テンプレート

```md
# 今週の振り返り

## できたこと
- 

## つまずきの傾向
- 

## 原因仮説
- 

## 次回までに戻るべき前提知識
- 

## 次の30分メニュー
1. 
2. 
3. 

## 実務で試す一手
- 
```

## 財務分析でのAIレビュー基準

```text
1. 数字の観察は正しいか
2. 分母・期間・単位を明記しているか
3. 事実と解釈を分けているか
4. 原因を断定しすぎていないか
5. 比較対象は妥当か
6. 事業構造と結び付いているか
7. 次に確認すべき情報があるか
8. 読み手が意思決定できる表現か
```

# 9. Webアプリの画面構成

## 9-1. 最低限の画面

```text

2. 学習マップ
3. 章・レッスン画面
4. 問題演習画面
5. 財務ワークスペース
6. 成果物ライブラリ
7. 振り返り画面
8. 設定・データ出力画面
```

## 9-2. ホーム

表示するもの。

```text
- 今日やる一手
- 今週の目標
- 学習継続日数ではなく「今週の完成成果物」
- 財務トラックの現在地
- 苦手スキル上位3つ
- 次に戻るべき前提知識
- 未完了の実務演習
- 直近のAI振り返り
```

### 重要な思想

「何日連続」のような連続記録を主役にしすぎない。

代わりに、以下を主役にする。

```text
理解した
解けた
つくれた
実務で使った
振り返って改善した
```

## 9-3. 学習マップ

- 樹形図で章を表示する
- 財務トラックはGate形式で表示する
- 章ごとに以下を見せる
  - 未着手
  - 読了
  - ドリル通過
  - 成果物提出済み
  - 再復習推奨
- 前提スキルが不足している場合は、ロックではなく「先にこれをやると楽」の導線にする

## 9-4. 章・レッスン画面

```text
上部: この章でできるようになること
中央: 本文、図解、例題
右または下部: 用語、前提、進捗、メモ
末尾: ドリル → スペシャル問題 → 実務演習 → 振り返り
```

## 9-5. 問題演習画面

- 問題文
- 表・グラフ・資料の閲覧領域
- 回答欄
- 自信度選択
- タイマーは任意
- 解答後に「どこで迷ったか」を一言で記録
- 解説は、即座にすべて見せず、自己説明を一度促す

## 9-6. 財務ワークスペース

財務は、読む画面と解く画面を分けずに、手を動かせるようにする。

```text
左: 決算情報・注記・資料
中央: 数値入力、表、グラフ
右: 観察／仮説／確認事項のメモ
下: 指標、競合比較、出所一覧
```

機能案。

- P/L、B/S、C/Fの簡易入力・表示
- 単位、期間、出所の入力を必須化
- 前年比・利益率・構成比の自動計算
- 3社比較
- 数字に紐づくコメント
- 「観察」「解釈」「仮説」「確認事項」の色分けではなくラベル分け
- 一枚の財務診断メモとしてMarkdown／PDF／PPTX用アウトラインに出力

## 9-7. 成果物ライブラリ

```text
- 依頼確認メモ
- 論点ツリー
- 財務診断メモ
- 競合比較
- 調査設計書
- 会議アジェンダ
- 議事録
- WBS
- 提案ストーリー
- 実行ロードマップ
```

各成果物に以下を紐付ける。

- 関連章
- つくった日
- 使った時間
- 自己評価
- レビュー履歴
- 実務転用の有無
- 次回改善点

## 9-8. 振り返り画面

```text
- 今週・今月の学習量
- 正答率ではなく、スキル別の状態
- 間違い方の分布
- できるようになったこと
- 未完了の成果物
- 次週の推奨メニュー
- AI振り返り履歴
```

# 11. 技術方針

## 11-1. 結論

最初からログイン・クラウド同期・AI評価まで作らない。

**Phase 1は「静的Webアプリ + Markdown/JSONコンテンツ + ブラウザ内保存 + JSON出力」**で始める。

理由。

- 教材の章立て・問題設計を先に検証できる
- ユーザー登録やサーバー運用なしで始められる
- GitHub Pages等の静的ホスティングでも運用しやすい
- 学習履歴を自分の端末に残せる
- 後からログイン、同期、AI機能を追加しやすい

## 11-2. 推奨アーキテクチャ

```text
[コンテンツ]
Markdown / MDX + JSON
        ↓
[フロントエンド]
React + TypeScript
        ↓
[ローカル保存]
IndexedDB
        ↓
[任意]
JSONエクスポート / インポート
        ↓
[将来]
認証・クラウド同期・AIレビューAPI
```

ブラウザに構造化データを保存する用途では、IndexedDBが候補になる。Web Storageよりも大きな構造化データを扱う用途向けのAPIであり、オフラインでの利用にも向く。  
参考: [MDN: IndexedDB API](https://developer.mozilla.org/ja/docs/Web/API/IndexedDB_API) / [MDN: IndexedDB の使用](https://developer.mozilla.org/ja/docs/Web/API/IndexedDB_API/Using_IndexedDB)

ReactからIndexedDBを扱う補助ライブラリの候補としてDexieがある。  
参考: [Dexie公式ドキュメント](https://dexie.org/docs)

## 11-3. 実装選択肢

### 選択肢A｜静的ファースト版：最初に作るべき

```text
React + TypeScript + Vite
Markdown / MDX + JSON
IndexedDB
GitHub Pages
```

向いていること。

- 個人利用
- オフライン寄り
- 学習ログのローカル保存
- コンテンツの高速な追加
- JSONバックアップ

避けること。

- 複数端末同期
- 複数人の共同編集
- サーバー側AI処理

### 選択肢B｜教材・アカウント・AIを統合する版：第二段階

```text
Next.js + TypeScript
MDX
認証
クラウドDB
AI API
```

Next.jsのApp Routerは、ファイルベースのルーティングとReactの新しい機能を使う構成として公式に案内されている。教材ページ、学習履歴、AIレビュー、管理画面を同じアプリに持たせる段階では候補になる。  
参考: [Next.js App Router](https://nextjs.org/docs/app)

### 選択肢C｜モバイル最適化を優先する版：将来

```text
PWA化
オフラインキャッシュ
ホーム画面追加
短時間ドリル中心のUI
```

## 11-4. 最初に採用する方針

```text
コンテンツ: Markdown / JSON
アプリ: React + TypeScript
保存: IndexedDB
公開: GitHub Pages想定
同期: なし
AI: なし。ただし回答ログの形式だけ先に設計する
出力: JSON / Markdown / CSV
```

この形なら、アプリを作り込みすぎず、教材の良し悪しを先に確かめられる。

# 12. MVPの定義

## MVPで絶対に入れるもの


# 14. 最初に作るべきコンテンツの優先順位

「全章の本文」から書き始めない。まずは、教科書としての勝ち筋が見える部分を作る。

```text
優先1: Gate 0｜数字の言葉

優先3: Chapter 9｜P/Lを読む
優先4: Chapter 12｜B/Sを読む

優先6: Chapter 14｜三表をつなげる
優先7: Chapter 18｜財務から仮説を立てる
優先8: Chapter 21｜財務分析総合演習
```

## なぜこの順か

```text
数字の基礎
  ↓
P/Lを読める
  ↓
B/S・C/Fで立体的に見える
  ↓
事業との接続ができる
  ↓
実在企業で論点を出せる
```

この一連が完成すれば、他領域を足す前にも、独立した財務学習アプリとして価値を検証できる。

# 15. コンテンツ制作の運用ルール

## 15-1. すべての章に必ず置くもの

```text
- なぜ学ぶのか
- 到達目標
- 前提知識
- 図解
- 例題
- ドリル
- 実務演習
- よくある間違い
- 振り返り
- 次へ進む条件
- 参考資料・出所
```

## 15-2. 財務章に追加で必ず置くもの

```text
- 用語の平易な説明
- 数式と、その式が答える問い
- 分母・期間・単位の確認
- 事業との接続例
- 断定してはいけない例
- 公開情報のどこを見ればよいか
- 競合比較時の注意
```

## 15-3. 情報源の優先順位

```text
第1層: 法定開示・決算資料・企業公式資料
第2層: 官公庁・取引所・業界団体
第3層: 一次取材・公式発表
第4層: 信頼できる報道・調査会社資料
第5層: 解説記事・個人ブログ
```

財務分析の演習では、まず企業の決算資料、適時開示、有価証券報告書を優先する。

日本企業の公開情報では、金融庁のEDINETとJPXの上場会社情報検索を基点にする。EDINETでは法定開示書類が公開され、JPXの上場会社情報検索では決算情報や適時開示などを確認できる。  
参考: [EDINET](https://disclosure2.edinet-fsa.go.jp/) / [JPX 上場会社情報検索](https://www.jpx.co.jp/listing/co-search/index.html)

## 15-4. 修正ルール

- 数字、固有名詞、制度、引用は出所を残す
- 外部リンクには確認日を残す
- 問題に使う企業情報は、対象期間を明記する
- 解答例は「唯一の正解」ではなく、評価基準を併記する
- 更新が必要な制度・会計基準・開示ルールは、バージョン履歴を残す

# 17. リスクと先回り

## リスク1｜教材が広すぎて、永遠に完成しない

対策。

```text
全章の本文を書かない。
まず、財務の縦切りプロトタイプを完成させる。
```

## リスク2｜問題数を増やしすぎて、解説が薄くなる

対策。

```text
問題数ではなく、間違いタグ・ルーブリック・再出題導線を優先する。
```

## リスク3｜AIが便利すぎて、考える前に答えを見る

対策。

```text
AIは回答後・自己説明後にだけ使う。
「答え」より「次に考える問い」を返す。
```

## リスク4｜学習ログの入力が面倒で続かない

対策。

```text
必須入力は4つだけ。
- 正誤
- 自信度
- 所要時間
- 一言メモ
```

## リスク5｜実務ケースが古くなる

対策。

```text
ケース本文と、時点依存の数値データを分離する。
問題データに対象期間・出所・確認日を持たせる。
```

## リスク6｜財務の正確さと、事業理解が分離する

対策。

```text
財務章のすべてに「事業との接続」「追加確認事項」を必須にする。
```
